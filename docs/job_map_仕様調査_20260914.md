## 0. 先に結論

添付3枚は、機能としては**1つの部品**の3つの見え方です。中身は

> **「フォローできる対象（エンティティ）の辞書」＋「コンテンツにその対象を紐付けた表」**

これだけです。フォロー画面も、Myニュースのフィードも、おすすめも、この2つの上に乗った
別々の SQL / 検索クエリにすぎません。**job_map ＝ この「フォローできる対象の辞書」**、
と置くのが一番きれいに収まります。

そして本サイトには、その辞書の中身がすでに言語化されています。

- `src/components/Method.jsx:36`（③）… 「求職者が打つ言葉を、**エリア・業態・職種・こだわりの4分類**で洗い出します」
- `src/components/Method.jsx:90`（⑩）… 「求人情報の**構造化データ**、ページごとのタイトル…**拠点や職種ごと**に分かれていないかまで見ます」

③で洗い出す4分類が、そのまま job_map の **entity_type** になります。
⑩でやりたい「拠点・職種ごとのページ分割」は、job_map があれば**自動生成**になります。
つまり job_map は新機能というより、**いま手作業でやっている調査結果を、機械が読める形に置き直したもの**です。

## 1. 添付から読み取れる機能の分解

### 添付1（フォロー追加）
| UI | 挙動 |
|---|---|
| 検索窓「企業・業界、トピック・コラム…」 | **フォロー対象**を検索（記事本文の検索ではない）。対象は複数の型が混ざって1本の窓に出る |
| 「話題のトピック」6枠 | いま伸びている対象。`熊本地震 1,181人` `個人向け国債 **1人**` が同列＝**フォロワー数の降順ではない** |
| 「登録数の多いトピック」 | `私の履歴書 240,494人` … こちらは**累計フォロワー数の降順**そのもの |
| 各カードの ⊕ | 1タップでフォロー追加。カード内に**フォロワー数**（社会的証明） |
| 上部タブ | 最新 / フォロー一覧 / フォロー追加 / 保存記事 / 閲覧履歴 の**横スクロールタブ** |

### 添付2（おすすめ18時）
| UI | 挙動 |
|---|---|
| 「本日分の更新は18時です」 | **リアルタイムではなく1日1回のバッチ生成**。この一文が仕様の核心 |
| 「今日の10本 ベータ版」 | 生成本数が固定（＝**枠＝スロットが先にあり、そこに候補を差し込む**方式） |
| 「あなたにおすすめ（**日経ID登録情報から**）変更する」 | 行動履歴ではなく**登録属性**が根拠。＝**コールドスタート対策**。しかも根拠を明示し、ユーザーが**上書きできる** |
| 「注目記事を読んでみよう！」（大画像1本） | スロットA＝画像付き1本 |
| 「見出しに目を通そう！」（見出しリスト） | スロットB＝見出しのみ複数本。記事に `#日経MJ #食品` の**タグ表示** |

### 添付3（最新＝Myニュースのフィード）
| UI | 挙動 |
|---|---|
| 記事リスト | フォロー対象に紐づく記事を**時系列降順**でマージした1本のリスト |
| 各記事の `◇ カラダづくり` | **どのフォローで入ってきたか**の表示。フィードの説明責任＋フォロー解除の導線 |
| `3日前` `8月28日` | 相対表示と絶対表示の切替（おおむね1週間で切替） |

**重要:** 添付3の記事はすべて `カラダづくり` 1つ。つまり**フォロー数が少ないとフィードが痩せる**。
これが後述する「初期フォローの押し付け」（オンボーディング）が必須になる理由です。

## 2. 裏側の仕組み

日経の実装そのものは非公開です。以下は **(a) 公開情報で裏が取れている点** と
**(b) この種のフィードを作るときの定石** を分けて書きます。
(a) の根拠は末尾の出所一覧。**nikkei.com への直接アクセスは本セッションのネットワークで遮断された**ため、
一次情報の原文にはあたれておらず、数値は検索結果の要約経由です（要再確認）。

### 2-1. データモデル（これだけで全画面が作れる）

```
entity           フォローできる対象         ← これが job_map
  id / type(職種|エリア|業態|こだわり|企業|連載) / name
  aliases[]      表記ゆれ・別名（後述）
  parent_id      階層（介護 > 介護福祉士 / 東京都 > 世田谷区）
  follower_count 非正規化（表示用の集計値）

content          記事・求人・コラム
  id / title / published_at / image / body

content_entity   ★中核。コンテンツ ⇔ 対象 の紐付け
  content_id / entity_id
  source         editorial(手動) | dict(辞書一致) | model(推定)
  confidence     推定の確からしさ

follow    user_id / entity_id / created_at
saved     user_id / content_id / created_at      ← 保存記事
history   user_id / content_id / read_at         ← 閲覧履歴
```

全画面がこの上の一問一答になります。

- 添付3（最新） … `content_entity WHERE entity_id IN (自分のfollow) ORDER BY published_at DESC`
- 添付1（登録数の多い） … `entity ORDER BY follower_count DESC`
- 添付1（話題の） … 後述のトレンド算出
- 保存記事 … `saved`
- 閲覧履歴 … `history`

### 2-2. いちばん難しいのは「紐付け」（content_entity をどう埋めるか）

機能の品質はUIではなく**ここ**で決まります。実務では3層を重ねます。

1. **明示タグ（editorial）** … 入稿時に人が選ぶ。精度100%、コストは運用側。**最初はこれだけでよい**
2. **辞書一致（dict）** … `aliases[]` を使った正規化マッチ。
   例：`保育士` に対し `保育教諭 / 幼稚園教諭 / ほいくし / 保育スタッフ` を別名として持つ。
   日経は自然言語解析ソフトで人名・会社名を抽出し、上場企業には**証券コード**を付けている（＝
   「トヨタ」「トヨタ自動車」「7203」を同一エンティティに寄せている）と公表されています。
3. **推定（model）** … 埋め込み or 分類器で候補を出し、`confidence` 以上を**人がレビューして確定**。

> 落とし穴：`看護` で `看護助手` まで拾う、`保育` で `保育園の給食調理` まで拾う。
> 除外語（NGワード）と、`parent_id` による「親でフォローしたら子も入る／入らない」の
> 明示的な設計が要ります。日経が業界フォローと企業フォローを分けているのは、まさにこの粒度問題です。

### 2-3. フィードの作り方 — 結論：**fan-out on read でよい**

SNS のタイムラインには「書き込み時に全フォロワーの箱へ配る（fan-out on write）」定石がありますが、
**ニュース／求人型はその逆で、読むときに引く（fan-out on read）方が有利**です。理由：

- フォロー対象数がユーザーあたり数十件程度に収まる（＝ `IN` 句が短い）
- 1本のコンテンツを**多数のユーザーが共有**する（配る方式だと同じ記事を人数分コピーすることになる）
- 配信取り消し・訂正・非公開化が即座に効く（配ってしまうと回収が要る）

実装は素直に SQL の `IN` + `ORDER BY published_at DESC` + カーソルページング。
規模が出たら Elasticsearch 等の `terms` クエリに置き換える（日経も記事配信基盤に Elasticsearch を使用と公表）。

**必ず要るのが重複排除**：1記事が複数のフォローに当たるので、`content_id` で畳んで
「どのフォローで入ったか」を1つ選んでバッジ表示（＝添付3の `カラダづくり`）。
選び方は「フォローが新しい順」か「confidence が高い順」。

### 2-4.「話題のトピック」の算出

`follower_count` の降順**ではありません**（添付1に `1人` が混ざっている）。定石は次のどれか、または併用：

- **増加速度**：直近24h/7d のフォロー増 ÷ 母数（前週比、または z-score）
- **記事供給量の急増**：そのエンティティに紐づく記事が急に増えた（＝ニュースが起きた）
- **編集の手動枠**：`熊本地震` `イラン軍事衝突` のような時事は、人が差し込んでいる可能性が高い

`1人` が出ている以上、**新規作成されたエンティティを一定期間だけ露出する枠**（新着枠）も
混ざっていると見るのが自然です。いずれにせよ**日次バッチで十分**で、リアルタイム集計は不要。
`follower_count` の表示も厳密である必要はなく、カウンタの非正規化＋定期再計算で足ります。

### 2-5. おすすめ（今日の10本）

- **生成タイミング**：1日1回（18時）。理由は計算コストだけでなく、**編集が中身を点検できる**こと、
  「毎日18時に来る」という**習慣化**、そして「更新は18時です」と言えば**空の画面を説明できる**こと。
- **根拠**：`日経ID登録情報から` ＝ 属性（業種・職種など）ベース。
  行動履歴が貯まっていない新規ユーザーでも初日から動く（**コールドスタート対策**）。
  貯まってきたら閲覧履歴ベース（協調フィルタ／埋め込み近傍）に寄せていくのが通常の進み方。
- **枠（スロット）方式**：「注目記事を読んでみよう！」（画像1本）＋「見出しに目を通そう！」（見出し複数）と、
  枠が先に決まっていて候補を差し込む。全部を推薦モデルに任せず、**枠ごとに違うロジック**（人気／新着／推薦）を
  混ぜられるのが利点。ベータ表記と「変更する」リンクで**外した時の逃げ道**も作ってある。

### 2-6. 閲覧履歴・保存・上限

- **閲覧履歴**は端末で記事表示イベントを取り、収集APIへ送って `history` に積む。端末間で揃えるには**ログインが前提**。
- **上限は必ず要る**（無いとフィードが破綻し、コストも読めない）。公開情報で確認できた日経の実例は
  **キーワード登録 10件 / 記事保存 3,000件**。job_map でも同種の上限を最初から決めておくべきです。

### 2-7. 誰のデータか（ID）

全部 `user_id` に紐づきます。ログインを持たない構成なら、`localStorage` のデバイスIDで代用し、
後からアカウントに**マージできる形**にしておく（マージ設計を後回しにすると作り直しになります）。

## 3. job_map への写像（HRパートナーの文脈に置き換える）

| 日経 | job_map |
|---|---|
| 企業・業界・キーワード・連載 | **職種・エリア・業態・こだわり条件**（＝ Method ③ の4分類そのまま） |
| 記事 | 求人票／採用コラム／社員紹介 |
| Myニュース（最新） | 「気になる条件の**新着求人**がまとまって届く」 |
| 保存記事 | 気になる求人（応募検討リスト） |
| 話題のトピック | いま募集が増えている職種×エリア |
| 今日の10本 | 条件に近い求人のダイジェスト（メール／LINE と相性が良い） |

### なぜこれが本業に効くか（フォロー機能の副産物の方が大きい）

job_map を作ると、**求職者向けフォロー機能より先に**次が手に入ります。

1. **職種×エリアのページを自動生成できる** … ⑩「拠点や職種ごとに分かれていないか」への直接の答え。
   辞書の直積からページを吐けば、手作業のページ量産が不要になる（※空ページの量産は逆効果なので、
   求人が存在する組み合わせだけ出す）。
2. **JobPosting 構造化データを機械的に付けられる** … Googleしごと検索の要件（⑩）。
3. **③のキーワード洗い出しの成果物が資産として残る** … 案件ごとに作り直さず、**辞書を横に使い回せる**。
   「簡単につけられるようにしたい」という要望に効くのはここ。**部品ではなく辞書が資産**です。

## 4. 「簡単につける」ための3段階

本サイトは **Vite + React の静的サイトで、GitHub Pages 配信・サーバなし・ルーティングなし・ログインなし**
（`README.md` / `src/App.jsx`）。フォロー機能はユーザーごとの状態を持つので、**Lv0 以外はサーバ側が要ります**。

### Lv0 — サーバなし（このリポジトリのまま／数日）
- `src/data/job_map.json`（辞書＋階層＋別名）と `src/data/jobs.json`（求人）を置く
- フォローは **localStorage**、フィードはブラウザ内 `filter`
- ビルド時に職種×エリアの**静的ページを生成**（SEO の実利はここで先に出る）
- できないこと：端末間同期／本物のフォロワー数／メール通知／レコメンド
- **デモとして見せるには十分**。まずこれで「何を作るか」を確定させるのが安全

### Lv1 — BaaS（Supabase 等／数週間）
- `entity / content / content_entity / follow / saved / history` を素直にテーブル化、行レベル制御でユーザー分離
- フォロワー数は集計ビュー＋日次更新、話題のトピックは日次バッチ
- 新着通知メール（フィードのクエリをそのまま夜間に回すだけ）
- GitHub Pages のままでも動く（フロントは静的、データは BaaS）

### Lv2 — 検索基盤＋推薦（必要になったら）
- 全文検索・シノニム辞書（表記ゆれの本命）・ファセット
- 属性ベース→行動ベースの推薦、18時バッチ

### このリポジトリに具体的に増えるもの（Lv0 想定）
```
src/data/job_map.json          辞書（entity）
src/data/jobs.json             求人（content + content_entity）
src/lib/jobmap.js              正規化・別名解決・マッチ
src/lib/follow.js              localStorage の読み書き（後で API 差し替え）
src/components/FollowButton.jsx
src/components/TopicGrid.jsx   添付1
src/components/Feed.jsx        添付3
scripts/build-job-pages.mjs    職種×エリアの静的ページ生成
```
ルーティングが今は無いため、ページを増やすなら **Vite のマルチページ構成**か
`react-router` ＋ GitHub Pages 用の 404 フォールバックの判断が要ります。

## 5. 設計上の要注意点

1. **空のフィードが最大の敵**。オンボーディングで初期フォローを3つ押し付ける（日経の「For You」も
   最初に3問聞いている）。フォロー0件時の画面を先に設計すること。
2. **粒度の設計を先に**。`介護` と `介護福祉士` の親子、`東京都` と `世田谷区` の親子で
   「親をフォローしたら子も入るのか」を決めないと、後から変えると全ユーザーのフィードが変質します。
3. **上限を最初に決める**（フォロー n 件／保存 n 件）。
4. **表記ゆれは辞書で吸収**。検索エンジンの類義語機能に頼り切らず、`aliases[]` を正典に。
5. **本サイトの文言ルール**（README「文言のルール」）は job_map の表示にもかかります。
   フォロワー数を出す場合は実数のみ、効果の保証や他社比較は書かない。
6. **求人データの出所**が未定だと全部止まります（下記）。
